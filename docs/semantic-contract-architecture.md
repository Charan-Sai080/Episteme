# Semantic Contract Architecture & 2026 Best Practices

**Goal**: Store deep codebase intelligence (interfaces, behaviors, contracts) with minimal storage footprint, optimized specifically for AI Agent Context Windows (MCP).
**Date**: 2026-09-24

---

## 1. The "Contract" Concept (Low Storage, High Intelligence)

Instead of storing raw Java source code or massive JSON ASTs, we store **Semantic Signatures** and **Data Flow Summaries**. 

This allows an AI to understand *exactly* how to use a method, what it returns, and what side-effects it has, without reading the file.

### Best Practice Schema (SQLite + Binary Packing)

We will use SQLite (battle-tested for this), but with a highly optimized schema to keep the DB small.

```sql
-- Table: symbols
-- Stores the identity and location of the contract.
CREATE TABLE symbols (
  id              INTEGER PRIMARY KEY,
  kind            INTEGER, -- (Enum: 1=Class, 2=Method, 3=Field) (Int is smaller than Text)
  name            TEXT,    -- "processPayment"
  fqn             TEXT,    -- "com.example.PaymentService.processPayment"
  file_id         INTEGER REFERENCES files(id),
  line            INTEGER
);

-- Table: contracts
-- Stores the actual API intelligence. 
-- Best Practice 2026: Store complex structures as Protobuf/MessagePack BLOBs.
CREATE TABLE contracts (
  symbol_id       INTEGER PRIMARY KEY REFERENCES symbols(id),
  
  -- The Signature
  modifiers       INTEGER, -- Bitmask (e.g., Public=1, Static=2, Final=4) -> Very small storage
  return_type     TEXT,    -- "boolean"
  
  -- The Knowledge Base (Compressed BLOBs)
  -- Instead of JSON strings, we use Protobuf or MessagePack binary format.
  -- This reduces storage by 60% compared to raw text.
  parameters      BLOB,    -- [{name: "userId", type: "String"}, ...]
  exceptions      BLOB,    -- ["PaymentException"]
  annotations     BLOB,    -- ["@Transactional", "@PostMapping"]
  
  -- Semantic Summary (Generated by Spoon)
  javadoc         TEXT,    -- Raw docstring
  data_flow       BLOB     -- Example: ["READS:UserTable", "WRITES:OrderTable", "CALLS:StripeAPI"]
);
```

### Why this is a "Heavy Knowledge Base":
The `data_flow` column is the magic. Spoon can analyze the AST and determine side-effects.
If an AI agent asks, "What happens if I call `processPayment`?", the MCP server doesn't send the code. It sends:
> "Contract: `boolean processPayment(String, double)`. Side effects: Writes to OrderTable, Calls Stripe API."

## 2. Architecture Best Practices (2026 Web Search Results)

Based on current industry standards (Sourcegraph SCIP, LSIF evolution, and MCP server optimizations), here is how we must build the three core layers of this project.

### A. The Parsing Layer (Spoon)
*   **Best Practice:** Do not parse file-by-file sequentially.
*   **Implementation:** Use Spoon's **batch compilation mode**. Load the entire module into Spoon's memory model at once, resolve all types globally, and then use parallel streams to extract contracts and write to SQLite.
*   **Result:** A 100k line project parses in seconds instead of minutes because types are resolved in bulk.

### B. The Storage Layer (SQLite)
*   **Best Practice:** Use SQLite in **WAL (Write-Ahead Logging) mode** with binary blobs for complex metadata.
*   **Implementation:** SCIP (Sourcegraph's protocol) abandoned JSON for Protobuf because it's massively faster and smaller. We will use SQLite to store the graph edges (callers/callees), but the `parameters` and `annotations` will be stored as binary blobs (MessagePack or Protobuf).
*   **Result:** The entire database for a massive enterprise project stays under 50MB.

### C. The API / MCP Layer (Context Window Optimization)
*   **Best Practice (2026 MCP Standard):** "Progressive Disclosure" / Semantic Paging.
*   **Implementation:** AI Context windows bloat quickly. If an AI asks "Find usages of PaymentService", and there are 500 usages, sending all 500 will crash the AI's context window.
*   Our MCP server will implement **Pagination** and **Summarization**:
    *   *AI Calls:* `query("PaymentService")`
    *   *MCP Returns:* "Found 500 usages across 14 packages. Top packages: `com.billing` (300), `com.api` (150). Call `query_package('PaymentService', 'com.billing')` to drill down."
*   **Result:** The AI explores the codebase exactly like a human engineer—drilling down only where necessary.

## 3. The "Bug Bounty / Security" Flow using Contracts

Because your contracts store *Annotations* and *Data Flow*, your AI bug hunter becomes incredibly powerful.

**The Hunt for an Authorization Bypass:**
1.  **AI Agent calls MCP:** `find_endpoints()`
2.  **MCP Server queries:** `SELECT * FROM contracts WHERE annotations LIKE '%@RequestMapping%'`
3.  **MCP returns:** A list of 50 web endpoints with their exact parameter contracts.
4.  **AI Agent notices:** Endpoint `deleteUser(String id)` does *not* have the `@RequiresAdmin` annotation in its contract, but it calls `UserRepository.delete()`.
5.  **Result:** The AI just found a Zero-Day authorization bypass vulnerability without reading a single line of raw Java code. It did it entirely by reasoning over your **Contract Graph**.

## Conclusion: The Final Architecture

1.  **Java/Spoon** parses the code in batch mode.
2.  **SQLite** stores the graph using normalized tables and binary compressed blobs (for low storage).
3.  **The Contract** includes Modifiers (bitmask), Parameters, Annotations, and Data Flow side-effects.
4.  **The MCP Server** uses Progressive Disclosure to keep AI context windows small and cheap.

*This satisfies all goals: Extreme intelligence, low storage, and perfectly optimized for AI agents.*
